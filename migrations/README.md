# Database Migrations

**Empty by design. No migrations exist because no tables exist.**

## Why nothing is here yet

Phase 1 provides database *plumbing* — engine, sessions, health check — but no
schema. Modelling instruments, prices, corporate actions and universes is
deferred until the point-in-time requirements are fully specified, because
retrofitting `published_at` semantics into an existing schema is far more
expensive than designing for them.

## What "Alembic-ready" means here

`src/indian_equity_research/database/base.py` defines a `MetaData` with an
explicit constraint **naming convention**:

```python
NAMING_CONVENTION = {
    "ix": "ix_%(column_0_label)s",
    "uq": "uq_%(table_name)s_%(column_0_name)s",
    "ck": "ck_%(table_name)s_%(constraint_name)s",
    "fk": "fk_%(table_name)s_%(column_0_name)s_%(referred_table_name)s",
    "pk": "pk_%(table_name)s",
}
```

This matters more than it looks. Without it, Alembic autogenerate emits
unnamed constraints; PostgreSQL then assigns its own names; and a later
migration that needs to `ALTER` or `DROP` that constraint cannot reliably
target it. Fixing the convention before the first table exists costs nothing.
Retrofitting it costs a painful migration on live data.

## Setting Alembic up (Phase 2, when the first table is designed)

```bash
uv add alembic
uv run alembic init -t async migrations   # or the sync template
```

Then in `migrations/env.py`:

```python
from indian_equity_research.database.base import Base
from indian_equity_research.config import get_settings

target_metadata = Base.metadata
config.set_main_option("sqlalchemy.url", get_settings().database_url.render_as_string(hide_password=False))
```

Note: pass the URL programmatically. **Never write a credential into
`alembic.ini`.**

## Rules for migrations, once they exist

1. Every schema change is a migration. No manual `ALTER` against any database.
2. Review autogenerated migrations by hand; autogenerate misses type changes,
   server defaults and constraint renames.
3. Every migration has a tested `downgrade`.
4. Data migrations are separate from schema migrations.
5. Migrations are immutable once applied anywhere. Fix forward.
