# 0001. Initial technology stack

Date: 2026-08-04
Status: Accepted

## Context

The project is a point-in-time research platform for Indian cash equities,
built and maintained by **one person**, operating on roughly **₹3 lakh** of
eventual research capital.

The data volume is small and will stay small:

| Dimension | Scale |
|---|---|
| Instruments | Few hundred (Nifty 100 → Nifty 200), a few thousand including delisted |
| History | 15–20 years |
| Frequency | Daily bars; intraday only for occasional execution analysis |
| Total volume | **Single-digit gigabytes** |
| Write pattern | One batch per day, after market close |
| Read pattern | Analytical scans; no concurrent users |
| Latency requirement | **None.** Signals are generated end-of-day; rebalancing is monthly. |

Three constraints dominate the design:

1. **Operational surface is a cost, not a feature.** Every service added is a
   service that can fail at 09:20 with no colleague to page.
2. **Correctness beats throughput.** The failure mode that matters is a silent
   point-in-time violation producing a beautiful, false backtest — not a slow
   query.
3. **Fixed running costs are material at this capital base.** Infrastructure
   spend is measured against a portfolio where a few thousand rupees a year is
   a meaningful percentage.

## Decision

Phase 1 adopts:

| Choice | Reason |
|---|---|
| **Python 3.12** | The data-analysis ecosystem. 3.12 for `StrEnum`, `datetime.UTC` and improved error messages, without adopting a version too new for library support. |
| **`uv`** | Fast, lockfile-based, and provisions the interpreter itself — so a contributor needs no system Python 3.12. One tool replaces pyenv + pip + virtualenv + pip-tools. |
| **`src/` layout** | Tests import the installed package, not a directory that happens to be on the path. Catches packaging defects immediately. |
| **PostgreSQL** | The point-in-time store. Real transactions, real constraints, real types (`numeric` for money, `timestamptz` for time), and mature temporal query support. Correctness of the state of record is the highest-value property in this project. |
| **SQLAlchemy 2.x** | Typed, modern API. Database-agnostic enough to test against, explicit enough to reason about. |
| **`psycopg` 3** | The supported PostgreSQL driver for SQLAlchemy 2.x. |
| **Alembic-ready (not yet installed)** | The declarative metadata carries a constraint **naming convention** from the first commit, which is what actually makes autogenerated migrations reversible. Alembic is added when the first table is designed, not before. |
| **Parquet (planned, Phase 2)** | Columnar storage for the immutable raw archive and analytical scans. Compresses well, preserves types, reads fast, needs no server. Analytical queries will use DuckDB over Parquet; PostgreSQL remains the state of record. |
| **Docker Compose** | One service, one file, one command. Reproducible local PostgreSQL without installing a database on the host. |
| **Local development environment** | No cloud, no static IP, no always-on host in this phase. Phase 1 needs none of it, and it would be pure cost. |
| **`ruff`** | Lint and format in one fast tool. Replaces flake8 + isort + black + several plugins. |
| **`mypy` strict** | Financial code fails in ways types catch: a `date` where a `datetime` was meant, an optional that is never checked, a unit confusion. |
| **`pydantic-settings`** | Typed, validated configuration with first-class secret handling. Configuration errors surface at startup with readable messages rather than at 09:25 as an `AttributeError`. |
| **Standard-library `argparse`** | Three read-only subcommands do not justify a CLI framework dependency. |
| **Standard-library `logging`** | Structured output is a formatter, not a library. A JSON logger can be added later if a log aggregator ever exists to consume it. |

## Alternatives considered

### Distributed computing — Spark, Dask, Ray
**Rejected.** The dataset fits comfortably in memory on a laptop. These tools
solve a scale problem this project does not have, at the price of a cluster to
operate and debug. Revisit only if data volume exceeds single-node memory by a
wide margin, which is not foreseeable for daily Indian equity bars.

### Streaming — Kafka, Redpanda
**Rejected.** There is no stream. There is one batch per day after market
close. A message broker would add a stateful service to guarantee delivery of
a file that is already durable on disk.

### Orchestration — Airflow, Dagster, Prefect
**Rejected for now.** The pipeline is a handful of ordered steps run once a
day. `systemd` timers or `cron`, plus a `jobs` table with idempotency keys,
provide scheduling and retry semantics at a fraction of the operational cost.
Revisit if the DAG exceeds roughly 20 interdependent tasks.

### Kubernetes
**Rejected.** One container on one host. Kubernetes would be the largest and
most failure-prone component in the system by a wide margin.

### Redis
**Rejected for now.** There is nothing to cache and no queue to run. Revisit
if a live intraday dashboard is ever built.

### SQLite instead of PostgreSQL
**Rejected.** Weak typing (no native `numeric` or `timestamptz`), limited
concurrency, and no server-side features for temporal queries. The state of
record for financial data justifies a real database. SQLite would also make
the eventual production environment differ from development.

### A document store (MongoDB, etc.)
**Rejected.** The data is relational and benefits from constraints. Schema
enforcement is the point, not an obstacle.

### DuckDB as the primary store
**Deferred, not rejected.** DuckDB is excellent for analytical scans over
Parquet and is planned for exactly that in Phase 2. It is not the right home
for the transactional state of record.

### Machine-learning libraries
**Rejected for this phase and the next several.** With roughly 200
effectively independent time periods, a flexible model will fit noise
perfectly. ML is a later experiment layered on a working, costed, honestly
benchmarked rules-based baseline — never a starting point.

### Technical-analysis packages (TA-Lib, pandas-ta)
**Rejected for this phase.** Every such indicator is a deterministic function
of price and volume and adds no information not already present. They may
later serve as feature transforms inside a validated model. Installing them
now would invite treating them as trading rules.

### Groww API client / any broker integration
**Rejected, and deliberately not scheduled.** This is a research and shadow
portfolio project. There is no execution requirement. Adding broker
connectivity would introduce credentials, a static-IP requirement, a
regulatory surface and a recurring subscription cost — in exchange for a
capability the project has decided it does not yet want. Execution, if it ever
happens, is manual and outside this system.

## Consequences

**Easier**
- A new machine is productive with `uv sync`; no system Python or database
  install.
- Configuration errors fail fast, at startup, with readable messages.
- Type errors are caught before runtime.
- The whole stack runs offline on a laptop; running costs are effectively zero.
- Reproducibility is achievable because the surface is small enough to control.

**Harder**
- PostgreSQL requires Docker for integration tests. Mitigated: integration
  tests skip cleanly when it is unavailable, so `make test-unit` always works.
- Strict mypy makes some third-party integrations more laborious.
- Deferring Alembic means the first migration needs deliberate setup.

**Accepted costs**
- Single-node processing caps eventual scale. Accepted: the cap is far above
  this project's data volume.
- No orchestration UI. Accepted: a daily log and an emailed report are enough
  for one operator.
- No execution capability. **Accepted deliberately** — see the project's
  feasibility research, which concludes that automated execution is not
  economically justified at this capital base.

## Revisit when

| Condition | Reconsider |
|---|---|
| Daily data volume exceeds single-node memory | Distributed processing |
| The pipeline exceeds ~20 interdependent tasks | An orchestrator |
| A live intraday dashboard is required | Redis, a long-running service |
| The first ORM table is designed | Installing and initialising Alembic |
| A rules-based baseline has passed out-of-sample validation | Machine learning |
| Capital and validated live results justify automation | Broker integration |
